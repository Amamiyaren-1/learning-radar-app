# 任务

你要为一个个人学习者产出一份**可读的项目分析报告**，正文回答五个问题：

1. 项目亮点与对照：它解决什么问题、哪里值得关注；与两个相关项目相比有什么区别；为什么选这些对照。
2. 对我的价值：能学到什么；可能形成怎样的演示或个人成果。
3. 开始条件：需要什么资源；我已有的条件与缺口。
4. 一个小实验：先复现哪个具体行为；建议改动什么；成功后能观察到什么。
5. 继续探索的材料：仓库、具体文档、示例入口和已知限制。

# 硬性要求

6. 每条 `claims`、`novelty`、`highlight`、`comparisons` 必须带 `evidence_ids`，编号只能取自上面的证据清单。
   初筛结论只说明为什么选中这个项目，**不能**当作证据使用。
7. 明确区分三类结论：`fact`（证据直接支持）、`vendor_claim`（项目方自述）、`inference`（你的推断）。
8. 不允许出现证据里没有的 Star 数、版本号、发布日期或性能数字；也不要把 Star 数当作质量证明。
9. 不允许输出 92/100 之类的装饰性评分，也不允许给出精确学习时长。
10. 与至少两个用途相近的项目对比，写清各自解决的问题、关键差异、适用条件、限制，以及**为什么选它作对照**（`why_this_comparator`）。
11. `highlight` 要说清项目解决什么问题、哪里值得关注，并给出 `evidence_ids` 与 `quote`；
   `novelty` 要区分首次发布、重要版本还是实质技术变化，给出时间；证据不足就写“证据不足”，不要把最近提交当成创新。
   即使kind=unclear、写“证据不足”，仍要引用本次实际审查的相关材料，说明它支持哪些内容、为什么不足以确认创新；不能删除evidence_ids/quote。没有合适的支持材料就保留缺口、接受拒绝，不凑引文或虚构首发/创新。
12. `highlight.items` 只挑 **1–2 个最值得理解的亮点**，每个亮点逐项讲清（允许写成完整段落，可以多句）：
   - `name`：亮点名称（可含术语，例如“持久执行（durable execution）”）；
   - `plain`：**用普通语言**说清它是什么，不要用另一串术语解释术语；
     如果涉及读者可能没学过的编程概念（接口、代理、注解、依赖注入、框架名等），
     **先按“输入 → 程序实际做了什么 → 输出”讲清一次实际调用过程，再给出术语**；
     类比只能用读者已接触过的东西（例如“填表格”“像 pip install 一样加依赖”），不要用另一个同样陌生的库来解释。
     短示例（不必每个字段都套用，只在首次解释陌生概念时用）：
     “你写下一个方法名，声明要一个字符串、给回一个字符串（输入）→ 库把这句话拼成给模型的文本、发出去、再取回结果（过程）→ 你在代码里拿到一段文字（输出）；这种写法叫接口，替你干活的实现叫代理。”
   - `scenario`：一个具体场景，说明**没有它会遇到什么问题**（可以是假设场景，但必须写明“假设场景”）；
   - `how`：根据已有证据说明项目**如何解决**，并明确指出哪些部分**尚未核验**；
   - `difference`：与相关方案相比**差在哪里**。**功能范围与使用条件**的差别可以用官方文档（README、文档站、发布说明）支持；
     但**性能、可靠性、易用性孰优**需要相应证据，没有就只能写“本次未核验到可比证据，不能判断优劣”，不能声称更先进；
     不要求每一条比较都有第三方评测；
   - `value`：写清“**能获得什么能力、能做出什么作品、与已有经验怎么衔接**”。
     **不要从“用过某语言”推断语言偏好**（档案里写明没有语言偏好）；技术栈差异只能写成**学习成本**（需要准备什么环境、工具链、额外时间）。收益确实有限时可以写有限，但要说明**有限在哪**，不要用一句“背景偏某语言所以有限”带过。
13. `value_for_user` 三部分都要写，每部分可以是完整的一两句话：`learn`（能学到什么）、
   `demo`（能否形成直观、可体验的演示）、`artifact`（可能形成什么属于用户自己的小改动或作品）。
   可展示性重要，但不允许用演示效果替代证据。
14. `mini_experiment.suggested_change` 是**建议用户尝试的改动**，不是项目已具备的功能：
   不要写成已完成或已验证的能力，也不要给它 `evidence_ids`；`boundary` 写明这次不做什么。
15. `explore_further` 给出 `repo`、`docs`、`example_entry`、`known_limits`；没有核验到的项写“未核验到”，不要编链接。
16. 开始条件写在 `difficulty.conditions` 里，覆盖四类：`runtime`（**运行时及版本，按目标实际技术栈写**，例如 Node.js 22+）、
    `os_support`、`gpu`、`external_cost`：
    - 材料里有明确说法：`status="evidence"`，给 `evidence_ids` 和**原样** `quote`；
    - 材料里没有：`status="unknown"`，`value` 写“未知（未在任何已取材料中找到）”，不要猜；
    - 只是你的推断：`status="inference"`，必须写 `basis`；
    - 与该技术栈无关：`status="not_applicable"`，`value` 写明“不适用（原因）”。
17. 正文的“开始条件”只由这一组条件与 `starting_conditions` 生成：不要再单独写一份环境描述，
    也不要在别的字段里重复环境要求，避免表格与正文互相矛盾。
11.1 `learning_action.executable` 必须显式写 `true` 或 `false`：**不要**用入口是不是链接、也不要靠措辞来推断。
    - `true`（本次确实提供了可执行动作）：`action` 写有证据支持的具体动作及前置条件，`entry` 必须是本次核验过的入口，`done_criteria` 必须写有依据、可观察的完成标准。文档步骤不等于实际跑通。
    - `false`（本次没有可执行动作）：允许 `done_criteria` 留空，也允许保留 README / 文档链接作为来源并写清缺口；
      “没有实际运行”本身不等于不能提出文档支持的动作；executable表示本次能否给出有依据、前置条件和完成标准的动作，verification.actually_ran仍为false。环境/入口/条件证据不足时继续false，不强填步骤。
      仍然**不要把采集限制说成项目缺陷**（例如“项目没有示例”“教程不完整”），也不要因为入口页没有代码块就断定没有可用示例。
18. API 与密钥：用户的可用通道见档案里的 `resources`。**不得**把用户没有的提供方密钥当成已满足；
    优先给出适用于已配置通道的做法；示例确实需要别的密钥时，必须写明这是“缺口/未核验到兼容路径”。
19. 正文里不要出现证据编号、commit、获取时间（这些留在附录）。需要用证据时用自然语言说明性质，
    例如“README 声称……，尚未实际验证”“发布说明里写了……，我们没有运行过”。
    任何假设场景、演示建议、个人改动都必须明确标为“建议/尚未实现”，不得写成项目已具备的功能、
    效果或兼容性。资料不足就具体说明缺什么。
13.1 措辞必须保留原文的限定范围，不得放大：
     - “核心没有必需运行时依赖”只能说核心部分，不能写成整个项目“零依赖”；
     - 项目方说“减少切换提供商的修改量”，只能照此表述，不能无依据写成“改一个参数就能切换”；
     - 场景里的风险与收益用限定口径（“可能”“在……条件下”“需要你自己验证”），不要写成必然结果；
     - 用户已有的通道与示例所需通道不一致时，只能写“**兼容性未核验**”，不能写成“不兼容”；
     - 网页抽取可能丢代码块，本次没取到示例**不能**推导出“教程没有可执行示例”；
     - 没找到创新证据只能写“**本次未发现创新证据**”，不能写成“没有创新”。
     - 不为显得有吸引力而夸大功能、收益或易用性。
20. 引文只能证明“材料里这么写”。不要把“支持 Linux”推断成“支持 Windows”，也不要从“没有提到”推出“不支持”；
    必须保留原文限定（例如“核心零必需运行时依赖”不能说成整个项目“零依赖”）。
21. 本层不运行任何项目：只说明查阅了文档还是源码。
22. 证据不足时不要勉强推荐：`recommendation.decision` 设为 `watch`，并在 `evidence_gaps` 里逐条写出缺什么。
23. `mini_experiment` 必须与第 1 节的亮点一致，并且**只能声称它实际涉及的能力**：
    换一个模型提供商、加一个计算器工具，都不等于验证了持久执行或可靠性；
    如果亮点讲的是持久执行，实验就要能观察到**任务中断与恢复**，否则就写明“本次实验不覆盖这一点”。
    **明确报错不算成功**：`observable` 必须写“成功时会看到什么”，报错只能作为排查线索。
    若用户已配置的通道（见档案 `resources`）与示例所需通道不一致且兼容路径未核验，
    必须把它写成**前置缺口**，不能靠“建议尝试”把它变成已可执行步骤。
    如果现有材料不足以设计这样的实验，就写“尚不能制定”，或把现有步骤明确标为**安装准备**。
24. 每条 `fact` 与 `vendor_claim` 必须带 `quote`：从所引证据里**原样抄一段连续**短文字（不超过 60 字，必须能逐字找到）。
    - 不得**拼接**（把两处文字合成一句）、不得**改写**（包括把“创建于 2026-…”写成 `created_at: 2026-…`）。
    - 版本号、发布日期、星数这类**元数据不需要引文**，直接写数值即可（程序会渲染结构化事实）；
      引文要求主要针对 README、发布说明、网页这类**文本证据**。
    - 写不出连续原文时，**不要**把事实降级为推断：换一条能引用的证据，或删掉这条结论。
25. `learning_action.entry`：`executable=true` 时只能使用上面“已核验的学习入口”里的 URL，禁止自己猜链接；
    `executable=false` 时可以留空，也可以保留已有的 README / 文档URL作为来源。entry只能是明确URL或空字符串；不得拼接括号、说明文字或“暂不可执行”，缺口说明写在action等文字字段。
26. 不需要输出 `verification` 字段：查阅状态由运行记录生成，你自报的状态会被覆盖并记入警告。
    该状态只表示“通过了某套检查”（读过哪些材料、是否运行过），**不代表内容正确**；正文不要把它表述为已核验。
27. 长度以**讲清楚**为准，不再限制单句长度：第 1 节的亮点解释与第 2 节的“对我的价值”可以写成完整段落。
    为了不被输出上限截断，其他字段保持简短（`claims` 不超过 5 条、`comparisons` 每个字段一两句），
    整个 JSON 控制在 3000 字以内；写完先自检 JSON 是否闭合。
28. 不要把证据摘录整段抄进输出，不要在字段里复述标题。JSON 必须完整闭合，结尾不要添加解释。
29. 上面“用户对相关项目的既有反馈”是**用户原话，不是证据**：不得用作 `evidence_ids`，也不得据此写事实结论；
    “不想进一步了解”不构成排除名单、语言偏好或长期兴趣规则；
    “读懂了项目做什么 / 看懂了亮点”只表示叙述可理解，不代表用户认可项目；
    不得跨项目推断偏好，也不要替用户解释原因。
